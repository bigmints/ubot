# Conversational collections verification plan

Date: 2026-09-14. Status: implementation verification plan, updated for revision 3: host extraction and an already-extracted-input engine; no collection feature acceptance or release verdict has been issued. Earlier planning review/validation artifacts are frozen evidence of their respective prior revisions and do not approve this revision. This verification-plan revision is author work, not an independent revision-3 review.

Quality owner: `collections_quality` (Factory quality-manager specialist). The implementation authors supply their checks; a different actor performs integration review on the implemented revision. This document defines evidence collection and risk coverage. Intended behavior and acceptance remain in the [canonical conversational collections specification](../../.factory/product/specs/conversational-collections.md), with exact revision 3 pending human approval. The [implementation plan](implementation-plan.md) and [stories](stories.md) project delivery from that contract.

## Evidence boundary and current baseline

This planning pass inspected the research, concierge profile and route authorization, attachment extraction, visitor tool filtering, current concierge tests, and packaging/startup source. It did not execute collection code, a model provider, a live visitor channel, or an installed release. The illustrative research UI is not application evidence.

Source observations that the implementation must address:

- `youbot-core/src/concierge/profile.ts` permits 30 knowledge notes and 30,000 total content characters and embeds enabled notes into the concierge prompt. Collections need their own retrieval path; copying extracted items into these notes cannot establish scale, isolation, or freshness.
- `youbot-core/src/api/routes/chat.ts` truncates text/PDF attachment content at 100,000 characters. The Youbot host import must retain the original and report extraction coverage rather than inheriting this as an invisible completeness limit.
- The same route coerces `parser.getText()` with `String(...)`. The installed `pdf-parse` v2 declaration returns `TextResult` with `text`, `pages`, and `total`; its result class has no observed `toString` override. A real text-PDF fixture must verify actual text/page extraction through the host PDF adapter. This is a source compatibility concern, not an executed defect verdict.
- `youbot-core/src/engine/tools.ts` currently limits visitor tools to an explicit allowlist. Adding read tools needs both registry exposure tests and execution-boundary authorization tests, including aliases and forged direct calls.
- Existing `answerFromKnowledge`, price/booking approval policies, owner takeover, and unknown-delivery behavior are regression boundaries. Publishing content must not silently change those policies.
- Current store tests cover durable inbox behavior, conflicts, idempotent replies, and owner route denial. They do not establish collections correctness. Youbot package staging uses prebuilt backend/static UI; source compilation alone does not prove the launched package contains the new migration, assets, or parser dependencies.

## Revision-3 package and host boundary

The package accepts already-extracted crude text, ordered segments or candidate records with provenance and explicit coverage metadata. It validates and persists those payloads, proposals, identities, revisions and publication state. Semantic organization comes from the host LLM/tool loop submitting explicit proposals; the engine does not run a semantic extraction model internally. The host authenticates callers, reads files, invokes external PDF/OCR/parsing libraries, stores originals, runs extraction jobs and the LLM loop, and submits bounded engine inputs through public APIs/tools.

There is no package file importer, PDF parser, OCR pipeline, blob/source-file port, parser port, import-job runner or mandatory extraction port. Engine replay/idempotency and payload validation are independent from host file/job retry. Host provenance identifiers are data references, not instructions for the package to open files or fetch URLs. A database adapter may perform its documented persistence I/O; it does not authorize source-file access.

Host PDF fixtures below retain the original Youbot acceptance coverage. Label their evidence **host pipeline**. Package fixture evidence starts from supplied extracted payloads and must not be presented as independent verification of source extraction completeness or accuracy.

## Test corpus and scoring

Use synthetic fixtures with checked-in expected facts and source locations; use consenting customer documents only with explicit handling/access scope. No real customer originals or credentials belong in test reports. Record fixture hashes and, for host-pipeline checks, the external parser/model version and extraction settings. Package checks instead record input-payload/schema/provenance versions and declared coverage. For probabilistic extraction, record each run separately and retain failures; a successful retry does not erase an earlier incorrect result.

The minimum corpus should include:

| Fixture | Required distinguishing cases |
| --- | --- |
| Property catalogue | Similar titles, stable property references, building/unit relations, unavailable and unknown availability, two currencies, rent versus sale, area units, missing prices, image-free listing. |
| Class catalogue | Course/session relation, per-session versus per-term prices, capacity described as a snapshot, recurring class, timezone, cancelled exception, ambiguous weekday/date. |
| General collection | New attributes, sparse records, long descriptions and policies that are useful without becoming items. |
| PDF coverage | Clean multipage PDF, content beyond character 100,000, multi-column layout, scan-only pages, mixed scanned/text pages, corrupt and password-protected PDFs. |
| Reimport sequence | Exact repeat, renamed file with same bytes, newer source revision, missing old item, changed strong ID, near duplicate, conflicting sources, prior owner correction. |
| Isolation/adversarial set | Two independent entities, private source passage, unpublished item, malicious instructions inside PDF/text, hostile HTML/link content, guessed source/item/job IDs. |

For the deterministic fixture set, require exact expected item IDs/counts, critical values, publication states and query result sets after owner review. Critical values include money/currency/basis, units, date/time/timezone and business availability. Uncertain input must produce explicit unresolved/unknown states, never guessed values. All published asserted fixture facts must have valid source or owner-edit provenance. Unauthorized content exposure and unauthorized mutations must be zero.

Report raw extraction misses, duplicates, critical-field errors, unresolved fields, source coverage, and owner correction effort separately. Do not invent a production extraction accuracy, latency, scale or cost guarantee from this small corpus. Benchmark per approved limits and the selected actual provider before making those claims.

For package reuse, maintain two independent consumer fixtures with different domain objects and host integrations: the Youbot adapter and a small unrelated headless host. The second host must not depend on Youbot, React, its route/session models, hidden workspace setup, or another consumer's authenticated context. Use host-owned temporary databases and distinct actor/tenant contexts. The independent engine consumer supplies extracted inputs directly and needs no source store, parser, job runner or model provider. Include at least two normalized tool-protocol fixture shapes; these prove adapter conformance, not live compatibility with two model providers.

## Execution sequence and completion gates

Revision-3 delivery uses CC-S13 for provider-neutral tools and preliminary packed-consumer smoke, CC-S11 for integrated first-host review, CC-S12 for final artifact preparation, and CC-S14 for the final independent aggregate gate. CC-S14 must review every original CC-S01–CC-S12 native acceptance criterion, every mandatory current-revision acceptance supplement, CC-S13 acceptance and all CC-01–CC-32 specification requirements. The original twelve Spacecrew acceptance arrays remain historical native criteria; completing them alone cannot establish revision-3 reusable-engine readiness. This sequence does not authorize implementation or publication.

1. **Contract checks during implementation:** authors demonstrate schema/migration integrity, typed validation, scope enforcement, extracted-input validation/replay, proposal lifecycle and exact query behavior on deterministic fixtures. Tests must inspect persisted outcomes and denial paths, not merely mirror implementation branches. Public core APIs and tools receive the same adversarial suite; passing only a Youbot route wrapper is insufficient.
2. **Integrated product flow:** a reviewer distinct from implementation authors runs host extraction → engine payload submission → source review → correction → publication → visitor answer → reimport conflict → undo/archive → restart. Cover properties, classes and fallback content with independent owner and visitor sessions. Compare preview and real visitor facts at a recorded revision.
3. **Provider and delivery checks:** separately run host external parser and supported model interactions, explicitly identifying any unavailable provider/channel checks. Source review, generated responses and mocked transport are useful evidence levels but cannot close a criterion requiring live recipient delivery.
4. **Installed package checks:** package and migration owner provides final artifact identity; quality executes the packed reusable engine outside the repository and the staged/installed Youbot flow against isolated data. Run both consumers with extracted inputs, no-file-side-effect checks, optional renderer isolation and supported compatibility fixtures. Separately verify the Youbot host PDF pipeline in its installed package. An old package, source import, development server or browser screenshot cannot prove the final package.
5. **Review and decision:** link each approved acceptance criterion to evidence, failed defects or a stated untested reason. A critical visibility, mutation, data-loss or fabricated-fact failure blocks the quality recommendation. Product acceptance and release permission remain separate human decisions; task/story assignment and check recording grant neither.

Run relevant existing concierge, security, tool registry/approvals, and channel regression checks as implementation touches those surfaces. Use the repository's actual package scripts and record commands/exit results at the tested revision. Broaden checks when changes or failures justify it, not to inflate test counts.

## Evidence record and handoff

Each check record should identify: canonical criterion and story; Q-scenario; source revision plus scoped dirty-file hashes if applicable; fixture hash; OS/runtime and artifact hash where relevant; actor/role; observed command or interaction; expected versus actual; outcome `passed`, `failed`, `not run`, or `blocked`; redacted artifact paths; and remaining evidence limitations. Use Factory/Spacecrew's supported evidence boundary when available rather than editing its internal records directly.

Keep evidence under the canonical test/report location selected in project authority, linked from the same work item. Do not introduce a parallel acceptance register or credentials/customer files in reports. If a required provider, installed OS or channel is unavailable, name it as untested and leave its dependent acceptance pending; do not replace it with an unrelated successful check.

The later quality verdict will separate source review, local execution, rendered UI, authenticated persistence, actual provider behavior, installed runtime and external delivery. Planning completion in this document proves only that scenarios and evidence expectations have been defined.
